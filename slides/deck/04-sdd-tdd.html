07 · Упражнение

«Добавить экспорт отчёта в Markdown»

Содержимое?·Пустой отчёт?·Знаки Markdown?·Ошибки?

Что объединяет эти вопросы?

Главная мысль

Название есть. Контракта нет.

Контракт — это договорённость о том, что должно получиться и как функция ведёт себя в разных ситуациях.

Без контракта каждый может сделать правильно — но по-своему.

Сказать: «Вот задача. Сразу видно, что нужно уточнить содержимое файла, пустые данные, знаки Markdown и ошибки. Но что объединяет все эти вопросы?» Выдержать короткую паузу и открыть модалку. «Всё это части контракта. Контракт — договорённость о результате и поведении функции. Без него каждый может сделать правильно, но по-своему». Переход: «Спецификация фиксирует такой контракт до начала работы».

08 · SDD

Спецификация фиксирует контракт

# Экспорт отчёта в Markdown ## Цель Разработчик может сохранить текущий отчёт в переносимом формате, прочитать его без приложения и добавить в репозиторий. ## Пользователь Разработчик, который просматривает сформированный отчёт. ## Границы - Экспорт работает локально и не обращается к внешним сервисам. - Результат — один файл `report.md` в кодировке UTF-8. - PDF, шаблоны оформления и загрузка в облако не входят в задачу. ## Контракт - Секции идут в порядке: заголовок → итог → найденные проблемы. - Пустые секции не добавляются. - Символы `#`, `*`, `[`, `]` из данных не меняют разметку документа. - Пустой отчёт — отчёт без итогового текста и найденных проблем. - Для пустого отчёта экспорт завершается сообщением «В отчёте нет данных», файл не создаётся. - Повторный экспорт заменяет существующий `report.md` только после того, как новый файл полностью сформирован. - Одинаковые входные данные всегда создают одинаковый файл: дата генерации и случайные значения не добавляются. - При ошибке записи неполный файл удаляется, пользователь видит причину. ## Пример результата ```markdown # Отчёт проекта ## Итог Найдена 1 проблема. ## Найденные проблемы - Не обработан пустой набор данных. ``` ## Критерии приёмки - [ ] Непустой отчёт создаёт UTF-8-файл с секциями в заданном порядке. - [ ] Специальные символы из данных отображаются как обычный текст. - [ ] Пустой отчёт возвращает понятное сообщение и не создаёт файл. - [ ] Повторный экспорт безопасно заменяет предыдущий `report.md`. - [ ] Два экспорта одинаковых данных создают одинаковое содержимое. - [ ] Ошибка записи не оставляет частично сформированный файл.

Прокрутите: ниже — контракт и проверяемые критерии.

Сначала показать цель, пользователя и границы. Затем прокрутить к контракту: «На прошлом слайде были вопросы — здесь записаны выбранные ответы». Остановиться на пустом отчёте и критериях приёмки. Не читать документ целиком. Переход: «Теперь эти критерии можно превратить в проверки».

09 · TDD

TDD превращает обещание в проверку

Пустой отчёт → «В отчёте нет данных» → файл не создан

Red
Проверка падает:
поведения ещё нет → Green
Минимальный код
выполняет обещание → Refactor
Улучшаем код,
обещание сохраняется

Один тест проверяет одно обещание, а не всю спецификацию.

Связать со слайдом 8: «Там мы записали обещание. Теперь до реализации записываем его проверку». Red доказывает, что проверка замечает отсутствие поведения. Green — добавляем только необходимое. Refactor — улучшаем код и сразу видим, сохранилось ли обещание. Один зелёный тест не доказывает, что выполнена вся спецификация.

10 · Вместе

Спецификация и тесты решают разные задачи

Спецификация
что и зачем → Критерии
что должно получиться → Тесты
работает ли поведение → Код
как это сделано → Проверка цели
то ли мы создали

Тесты могут быть зелёными, а продукт — не тем.

Пройти цепочку слева направо. Спецификация задаёт направление, критерии описывают результат, тесты проверяют отдельное поведение, код его реализует. В конце отдельно проверяем цель целиком. Переход: «Теперь нужно сохранить связи между требованиями, решениями, кодом и тестами».
