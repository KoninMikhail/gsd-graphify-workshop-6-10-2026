# План воркшопа

## 1. Цель встречи

Показать не набор команд, а воспроизводимый способ разработки с AI-агентами:

> Намерение → спецификация → план → реализация → тесты → проверка → обновлённое знание о проекте.

Главный результат встречи — участник понимает, какую проблему решает каждый элемент процесса и может начать с минимального workflow, не внедряя всё сразу.

## 2. Драматургия

### Акт I. Боль

Мы ускорили генерацию кода, но получили новые проблемы:

- контекст разбросан между чатами, файлами и головами;
- агенту приходится заново восстанавливать рабочий контекст через поиск,
  индекс и чтение выбранных фрагментов;
- текстовый поиск находит упоминания, но не гарантирует восстановление причин,
  истории и связей между решениями;
- решения забываются или противоречат друг другу;
- агент уверенно реализует не то;
- длинный memory bank становится архивом, а не рабочей памятью;
- завершённая задача не означает достигнутую цель.

Вопрос акта: **как сделать AI-разработку управляемой, а не просто быстрой?**

### Акт II. Принципы

- SDD фиксирует намерение, ограничения и критерии результата.
- TDD переводит часть ожиданий в исполняемую форму.
- План связывает спецификацию с конечными изменениями.
- Проверка оценивает достижение цели, а не число закрытых задач.

Вопрос акта: **какой процесс удержит эти элементы вместе?**

### Акт III. Инструменты и доказательство

- GSD организует жизненный цикл работы.
- Graphify строит навигационный слой по сущностям и связям проекта.
- Live-demo проходит один короткий путь от требования до проверки.

Финальный вопрос: **что из этого участник попробует в следующей задаче?**

## 3. Тайминг основной программы

| Время | Мин | Блок | Результат |
| --- | ---: | --- | --- |
| 00:00–00:08 | 8 | Открытие | Обещание встречи, знакомство, быстрый опрос |
| 00:08–00:20 | 12 | Наши боли | Участники узнают собственные проблемы |
| 00:20–00:32 | 12 | Почему memory bank перестаёт помогать | Понятна системная причина, без демонизации подхода |
| 00:32–00:45 | 13 | SDD + TDD | Понятны роли спецификации и тестов |
| 00:45–00:57 | 12 | Graphify | Понятны граф, связи, provenance и область применимости |
| 00:57–01:10 | 13 | GSD | Понятны milestone, phase, plan и цикл выполнения |
| 01:10–01:15 | 5 | Пауза / перезапуск внимания | Вопрос аудитории, подготовка демо |
| 01:15–01:25 | 10 | Установка и настройка | Участники видят минимальный путь запуска |
| 01:25–01:45 | 20 | Live-demo | Один workflow проходит от контекста до проверки |
| 01:45–01:50 | 5 | Разбор демо | Зафиксировано, что именно дало результат |
| 01:50–02:00 | 10 | Вопросы и завершение | Ответы, следующий шаг, обратная связь |

## 4. Баланс форматов

- Рассказ и история: 45 минут.
- Объяснение инструментов: 25 минут.
- Установка и live-demo: 30 минут.
- Пауза, взаимодействие и вопросы: 20 минут.

Каждые 10–15 минут менять режим: история → схема → вопрос → артефакт → демо.

## 5. Сквозной пример

Рекомендуемый пример — маленькая существующая программа, в которую нужно добавить проверяемую возможность:

> «Добавить экспорт отчёта в Markdown с предсказуемым порядком секций и понятной ошибкой для пустых данных».

Почему пример подходит:

- требование легко понять без знания домена;
- есть неоднозначности, которые выявляет discuss/spec;
- поведение удобно выразить тестами;
- изменение помещается в 15–20 минут;
- связи между требованием, планом, кодом и тестом можно показать в графе.

Не использовать в live-demo аутентификацию, платежи, сложный UI, внешние API или миграции: они создают шум и непредсказуемость.

## 6. Ключевые контрасты

Использовать контрасты вместо длинных определений:

| Неуправляемый подход | Управляемый подход |
| --- | --- |
| «Агент, сделай фичу» | Явные требования и границы |
| Чат как источник истины | Версионируемые проектные артефакты |
| Длинный memory bank | Структурированные документы + связи |
| «Код скомпилировался» | Проверены критерии результата |
| Один гигантский план | Малые планы с зависимостями |
| Магия инструмента | Наблюдаемый процесс и audit trail |

## 7. Интерактивные точки

1. В начале: «У кого агент уже забывал решение, принятое вчера?»
2. После memory bank: попросить назвать момент, когда документ перестал быть полезным.
3. Перед SDD/TDD: показать неоднозначное требование и попросить найти три трактовки.
4. Перед demo: аудитория выбирает один из двух заранее безопасных вариантов поведения.
5. В конце: «Какой один элемент вы попробуете на следующей задаче?»

## 8. Критерии успеха

Воркшоп успешен, если:

- основная программа закончилась не позднее 01:50, оставив 10 минут на вопросы;
- live-demo уложился в 20 минут или fallback был включён за 60 секунд;
- участники могут своими словами развести роли SDD, TDD, GSD и Graphify;
- минимум половина аудитории формулирует конкретный следующий эксперимент;
- ни один раздел не превращается в чтение документации с экрана.

## 9. Что сознательно не включать

- полный справочник всех GSD-команд;
- глубокую теорию графов;
- сравнение со всеми альтернативными фреймворками;
- сложную настройку моделей и интеграций;
- автоматическое выполнение большой фазы;
- заявления, что один подход подходит любому проекту.
