# Runbook live-demo

## Цель

За 20 минут показать не «как агент печатает код», а как одна неоднозначная задача проходит через явные решения, план, тест, реализацию и проверку.

## Демонстрационная задача

> Добавить экспорт отчёта в Markdown с фиксированным порядком секций и понятным поведением для пустых данных.

Минимальные критерии:

1. Заголовок и секции выводятся в согласованном порядке.
2. Специальные символы не ломают Markdown.
3. Для пустого отчёта система либо возвращает понятное пустое состояние, либо явную ошибку — вариант выбирается до реализации.

Проект должен быть маленьким, локальным и не зависеть от сети, базы данных, контейнеров или внешнего API.

## Что подготовить заранее

- Исходный проект в `project/` с зелёными тестами.
- Отдельная demo-ветка без незакоммиченных изменений.
- Зафиксированные checkpoints:
  - `demo/00-start`;
  - `demo/01-context`;
  - `demo/02-plan`;
  - `demo/03-test-red`;
  - `demo/04-implementation`;
  - `demo/05-verified`;
  - `demo/06-graph`.
- Открытые вкладки: требование, код, тест, `ROADMAP.md`, `PLAN.md`, отчёт Graphify.
- Локально сохранённый HTML-граф.
- Скриншоты каждой контрольной точки.
- Текстовый файл с командами для копирования без опечаток.

Теги или ветки — рекомендация; конкретный механизм выбрать заранее и не менять в день выступления.

## Команды, которые нужно проверить

Актуальные установленные навыки указывают:

```bash
npm i -g get-shit-done
```

Основной учебный путь:

```text
/gsd-new-project
/gsd-config
/gsd-discuss-phase 1
/gsd-plan-phase 1
/gsd-execute-phase 1
/gsd-verify-work 1
```

Graphify внутри GSD:

```text
/gsd-graphify build
/gsd-graphify status
/gsd-graphify query <term>
/gsd-graphify diff
```

Важно:

- перед выступлением проверить точный синтаксис на чистой машине;
- не запускать установку по сети в основном demo;
- не смешивать `/gsd-graphify` с standalone-командой `graphify` без объяснения;
- интеграция GSD требует включённого `graphify.enabled` в `.planning/config.json`;
- в текущей реализации GSD graph-артефакты находятся в `.planning/graphs/`.

## Поминутный сценарий

### 00:00–02:00 — Поставить задачу

Показать исходное требование и спросить аудиторию:

> «Что делать при пустом отчёте: вернуть заголовок с пояснением или ошибку?»

Оба варианта должны быть заранее подготовлены. Выбор меняет только один критерий и один тест.

Фиксируем решение. Проговариваем: «Первое полезное действие — не код, а снятая неоднозначность».

### 02:00–05:00 — Показать контекст проекта

Открыть:

- `PROJECT.md`;
- соответствующий фрагмент `REQUIREMENTS.md`;
- фазу в `ROADMAP.md`.

Не читать файлы полностью. В каждом показать по одной строке и объяснить роль.

Контрольный вопрос:

> «Где через неделю другой разработчик увидит принятое сейчас решение?»

### 05:00–08:00 — Обсудить и спланировать

Запустить или показать результат:

```text
/gsd-discuss-phase 1
/gsd-plan-phase 1
```

В `PLAN.md` выделить:

- ожидаемый результат;
- файлы или компоненты;
- зависимости;
- способ проверки;
- границы scope.

Если генерация занимает больше 45 секунд, переключиться на `demo/02-plan`.

### 08:00–11:00 — Сделать критерий исполняемым

Открыть заранее подготовленный или сгенерированный падающий тест.

Показать:

1. название теста как спецификацию поведения;
2. ожидаемый результат;
3. фактическое падение.

Запустить только узкий тест. Не запускать всю тяжёлую suite.

Ключевая фраза:

> «Красный тест здесь полезен: он доказывает, что критерий ещё не реализован».

### 11:00–15:00 — Реализовать минимальное изменение

Запустить интерактивное выполнение или показать результат запланированного шага:

```text
/gsd-execute-phase 1 --interactive
```

Для сцены интерактивный режим предсказуемее автоматической параллельной фазы: видны checkpoints, ниже расход и проще контролировать темп.

Показать маленький diff. Не разбирать синтаксис построчно; связать изменение с критерием.

Снова запустить узкий тест, затем короткую общую проверку.

### 15:00–17:00 — Проверить цель

Показать:

```text
/gsd-verify-work 1
```

Объяснить отличие:

- execution сообщает, что задачи выполнены;
- verification проверяет, достигнут ли обещанный результат.

Если обнаружен gap, не чинить его в прямом эфире. Показать, что gap становится входом нового плана.

### 17:00–19:00 — Показать Graphify

Использовать заранее построенный граф:

```text
/gsd-graphify status
/gsd-graphify query export
```

Показать путь:

`requirement → plan → implementation → test`

Открыть источник одной связи и уровень уверенности. Если live query нестабилен, открыть сохранённый `graph.html`.

### 19:00–20:00 — Закрыть цикл

Вернуться на слайд «Что произошло на самом деле».

Сказать:

> «Ценность не в количестве созданных Markdown-файлов. Ценность в том, что каждое решение оставило проверяемый след и следующий агент может восстановить путь».

## Правило переключения на fallback

Перейти к подготовленному checkpoint, если:

- команда не дала полезного вывода за 45 секунд;
- сеть, авторизация или пакетный менеджер запросили вмешательство;
- агент ушёл за пределы demo scope;
- тест падает по причине, не связанной с демонстрируемой фичей;
- осталось менее 8 минут, а реализация ещё не началась.

Фраза без оправданий:

> «Чтобы не тратить ваше время на ожидание, переключаюсь на заранее сохранённый результат этого шага».

## Три уровня fallback

1. **Checkpoint:** перейти на подготовленный commit/tag и продолжить live.
2. **Артефакты:** показать готовые `PLAN.md`, diff, тест и graph query.
3. **Скринкаст/скриншоты:** пройти историю без запуска инструментов.

Fallback — часть профессиональной подготовки, а не провал демонстрации.

## Что не делать во время demo

- не устанавливать зависимости;
- не обновлять GSD или Graphify;
- не вводить секреты;
- не ждать длинную генерацию молча;
- не чинить случайную проблему дольше минуты;
- не принимать непредусмотренное архитектурное решение;
- не показывать файлы с реальными токенами, внутренними URL или данными клиентов;
- не давать агенту менять десятки файлов ради маленькой фичи.

## Definition of ready

Demo готово, если:

- оно трижды подряд укладывается в 20 минут;
- полностью работает без сети после установки;
- каждый checkpoint можно открыть менее чем за 15 секунд;
- шрифт читается с последнего ряда;
- в проекте нет секретов;
- fallback отрепетирован вслух;
- выбор аудитории не создаёт неизвестную ветку сценария.
